# Real-cook test, 2026-10-18

First monitored cook with the bridge on a real grill: a Pit Boss PB850PS2
(`PBL` control board), read over BLE from a Linux Mint laptop a few metres away.
Raw logs, the database and per-minute samples are kept outside the repo.

## Setup

- `master` at b4067ba plus the Unauthorized retry from #4 (uncommitted at the time).
- Laptop: Linux Mint 22.3, BlueZ 5.72, Python 3.12, pytboss 2026.8.6, bleak 0.22.3.
- Grill firmware: Mongoose OS 2.19.1 (build 20210806), PB firmware 0.5.7.
- Two probes: probe 1 inside the grill, probe 2 outside in ambient air.

## Results

| Stage | Result | Evidence |
|---|---|---|
| 1. Start-up | Pass | `moduleIsOn`, fan, igniter and auger followed the grill within seconds. `grillTemp` and `grillSetTemp` matched the display. The auger reports 10-20 s bursts about once a minute. |
| 2. Setpoint change | Pass | Dial 190 -> 210 appeared in `grillSetTemp` within 10 s. |
| 3. BLE drop (`systemctl restart bluetooth`) | Pass | Recovered by itself in ~13 s on the first retry (5 s backoff). `reconnect_count` went to 1 and data never went stale. |
| 4. Long cook | Not run | The cook was ended early with a BLE turn-off (below). |

Readings arrived about every 7 s. The only gaps over 10 s during the test were
the planned ones: a bridge restart, the drop test, and a deliberate stop to send
the turn-off command.

## Findings

### Spurious Unauthorized over BLE

With the correct grill password, `PB.GetState` was rejected with
`Unauthorized` every 30-80 s, more often during cool-down. Before #4 each
rejection dropped the BLE connection, so the bridge could not stay connected
for more than about 10 s. With the retry in #4, every rejection recovered on
the second attempt and none caused a disconnect.

pytboss mixes the grill's uptime, in 10 s buckets, into the password and
extrapolates that uptime from a cached reading. Slow BLE round trips leaving the
estimate in the wrong bucket is the likely cause: over the local HTTP RPC (below)
the same grill gave 0 rejections in 20 polls.

### The grill rotates its BLE address

It advertised a different address on almost every connection. The bridge
matches by name (`PITBOSS_DEVICE_NAME`), which handled this. Anything keyed
on the address would break.

### Fields

- Always populated: power, fan/igniter/auger, error flags, `grillTemp`,
  `grillSetTemp`, `isFahrenheit`, `p1Temp`/`p2Temp` once a probe is plugged in.
- `smokerActTemp` was never populated, and `p3Temp`/`p4Temp` are always `null`
  (the model has two probe ports).
- `p1Target` stayed at 50 throughout; it looks like an unset default rather
  than a real target.
- No error flags turned on at any point.

### Turn-off over BLE works

`PitBoss.turn_grill_off()` (the `turn-off` MCU command, authenticated) was
accepted on the first try. The grill went to `moduleIsOn: false` with the fan
still running, its normal shutdown cycle, and the fan stopped about 10 minutes
later. The first state frame after the command came back blank, because the
firmware clears its status cache after sending an MCU command. The bridge
itself is still read-only; this was a one-off script.

### WiFi / local HTTP RPC

The grill was on WiFi, with Mongoose's HTTP server enabled (`http.enable: true`).
`pytboss.http.HttpConnection` read state 20/20 times, with average latency
0.63 s and no Unauthorized rejections. That makes WiFi a candidate source:
no BLE range limit, no one-connection limit, and no vendor cloud.

**Caution:** the local HTTP RPC is unauthenticated for configuration calls, so
anything on the same network can read the grill's configuration, including its
stored WiFi credentials. Keep the grill on an isolated or IoT network.

## Issues found in the test tooling

- The summary one-liner in the test handoff fails on Python 3.12: `\"` inside a
  single-quoted shell string reaches Python as a literal backslash inside an
  f-string expression. Use `%` formatting or a script file instead.
- `sudo` cannot prompt from Claude Code's `!` prefix. Run `sudo systemctl
  restart bluetooth` in a normal terminal.
